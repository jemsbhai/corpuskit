# CorpusKit Capability Traceability Matrix

Status: Draft baseline
CorpusGen compatibility baseline: `corpusgen==0.1.7`
Last audited: 2026-08-12

This document is the production traceability source for CorpusKit's promise to expose and demonstrate the complete public capability set of CorpusGen. Requirement IDs and acceptance-test IDs are stable and must not be reused after deletion. A requirement may move from `Planned` to `In progress`, `Implemented`, `Verified`, or `Deferred`; `Verified` requires the listed automated acceptance test to pass in its declared runtime profile.

Every row inherits its user/operator documentation, bounded telemetry, accountable owner role and
supported failure-mode contract from the machine-checked
[capability operational ownership map](capability-operations.md).
Every acceptance-test ID is also bound to exact executable test symbols in the
machine-checked [acceptance evidence registry](acceptance-evidence.json); entries marked
`partial` must correspond to non-Verified rows and state the remaining qualification gap.

## Runtime profiles

| Profile      | Required environment                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------------------- |
| `PLATFORM`   | CorpusKit application services, database, object storage and job runner; no CorpusGen operation required        |
| `CORE`       | Base CorpusGen install plus eSpeak NG 1.49 or later for G2P-dependent work                                      |
| `DATA`       | `CORE` plus the pinned, checksum-verified PHOIBLE cache                                                         |
| `OPT`        | `DATA` plus `corpusgen[optimization]` (`pulp`, `pymoo`)                                                         |
| `REPOSITORY` | `DATA` plus `corpusgen[repository]` (`datasets`, `huggingface-hub`)                                             |
| `LLM`        | `DATA` plus `corpusgen[llm]`, provider network access and a server-managed connection credential where required |
| `LOCAL_CPU`  | `DATA` plus `corpusgen[local]`, a compatible Hugging Face causal LM and sufficient CPU/RAM                      |
| `LOCAL_GPU`  | `LOCAL_CPU` plus a compatible CUDA runtime/GPU; bitsandbytes is required for 4-bit or 8-bit quantization        |

## Classification rules

- `Sync` operations must complete within the request budget and may be used for previews or small inputs.
- `Async` operations must run as durable jobs with progress, timeout, cancellation, retries where safe, persisted outputs and recoverable failure state.
- `Hybrid` means a small deterministic preview may run synchronously, while production-sized work must use a durable job.
- Secrets must be encrypted at rest, redacted from logs and never returned to clients after creation.
- Every result manifest must record the CorpusGen version, runtime profile, language, target source, unit, all algorithm/model parameters, seed when applicable and input artifact digest.

Project/corpus workspace persistence is a CorpusKit platform capability rather than a
CorpusGen symbol, so it is not added to the 75-row engine parity count above. Create/list,
bounded version-1 import, append-only manual/file version creation with server-owned parent

acceptance tests cover the create/import/version/export slice. Owner/admin-only project
deletion now uses exact accessible confirmation, immediate fail-closed logical removal,
transactional artifact tombstones, a configurable minimum 30-day retention, maintenance-only
byte-first physical purge, exact quota release, and durable audit evidence. SQLite race tests and
the opt-in real PostgreSQL RLS suite cover its service boundary. The migrated real-stack
Playwright deletion flow remains a release gate. Metadata update, individual corpus deletion,
and deletion undo remain unimplemented.

Tenant isolation, quota accounting, and audit evidence are also CorpusKit platform controls,
not CorpusGen parity rows. Current evidence forces PostgreSQL RLS on every persisted resource
table under distinct non-owner roles, verifies concurrent CPU/expensive admission and storage/
sentence/per-run ceilings, and chains the implemented mutation audit set transactionally.

RLS, and maintenance cleanup; SQLite and real concurrent PostgreSQL 17 acceptance cover that
boundary. Candidate-environment load, failover, edge/WAF, and alert-delivery evidence remains a
release gate. Billing, externally anchored audit retention, and backup/erasure drills remain
separate explicit gates.

## Product boundary disclosures

CorpusGen is a text and phoneme corpus engine. It does not provide authentication, authorization, tenancy, a web server, persistence, background orchestration, secret storage, audit logs, quotas, billing, audio recording, forced alignment, speech synthesis or acoustic evaluation. CorpusKit must supply those application capabilities without representing them as CorpusGen features.

CorpusGen also explicitly does not yet implement neural or Epitran G2P, full Phonetic Completeness Score, or full contextual/prosodic Phonological Contextual Diversity. These may be future CorpusKit roadmap items, but they are outside this baseline and must not be advertised as available.
